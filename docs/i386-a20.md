# Native A20 and extended-memory bring-up

`Kernel/I386/A20.HC` implements the boot-time A20 check and enable sequence in
HolyC compiled for i386. It requires code and stack below 1 MiB, interrupts
disabled, exclusive hardware access, and writable RAM covering its scratch
addresses. Call it before initializing keyboard/mouse input or allocating the
scratch region. It makes no BIOS calls in protected mode.

`I386A20Test()` distinguishes physical bytes at 0x5100 and 0x105100 using two
opposite write/read patterns. Both original bytes are restored, including when
the addresses alias because A20 is disabled. The checks require successful reads
of the written patterns, so an all-ones unmapped read is not sufficient to pass.
The caller must still establish that these are RAM addresses before writing them.

`I386A20Enable(allow_fast=FALSE, poll_limit=100000)` returns:

| Result | Meaning |
| --- | --- |
| 0 | Invalid polling limit or A20 could not be verified |
| 1 | Already enabled |
| 2 | Enabled through the keyboard controller |
| 3 | Enabled through the explicitly permitted port-0x92 fallback |

The controller path drains pending output, waits for input readiness, sends
command 0xD1, and writes the standard boot output-port value 0xDF. That deasserts
reset and enables A20. It is an initialization sequence, not a runtime operation
that preserves every controller output bit or queued keystroke. This hardware
sequence is also used by [Linux's boot A20 implementation](https://github.com/torvalds/linux/blob/master/arch/x86/boot/a20.c);
the controller command and output-bit meanings are visible in
[QEMU's 8042 implementation](https://github.com/qemu/qemu/blob/v10.2.1/hw/input/pckbd.c).

Polling is bounded by iteration counts, with I/O reads between polls. Repeated
all-ones status reads terminate early. This is not a calibrated millisecond
timeout. A zero polling budget skips controller writes and allows testing failure
or the fast fallback. Port 0x92 is disabled by default; when explicitly allowed,
its reset-request bit is cleared before writing. Every successful method must
pass the memory check; writing a control bit alone is never reported as success.
A controller timeout can leave its command sequence incomplete, so later input
initialization must establish its own controller state.

## Extended arena selection

`I386BootArena` now accepts an optional final `extended` Boolean. Its default
retains conventional-only selection. A caller setting it true must have verified
A20 and established a machine profile where the AH=88h report describes contiguous
RAM above 1 MiB, with additional device reservations supplied explicitly.

The extra candidate begins at 0x110000, reserving the first 64 KiB of extended RAM
for boot scratch. It ends at the reported limit or 0xF00000, whichever is lower.
The conservative ceiling avoids the legacy 15–16 MiB device window and stays below
the 386SX physical-address ceiling; it does not assert that every machine has that
window occupied. Both conventional and extended candidates subtract the caller's
reservation union, and the largest remaining gap wins. Missing, zero, or too-small
extended reports leave the conventional candidate available.

VGA and loader fixtures verify A20 before opting in. Their 8 MiB QEMU profiles
now explicitly require an arena above 1 MiB: VGA uploads from that framebuffer,
and the native loader executes allocated modules in that memory. The selection
API does not itself enable hardware or treat a caller Boolean as hardware evidence.

## Verification and remaining work

`python3 tools/test-i386.py --a20` forces both emulated A20 control sources off,
verifies aliasing, exercises zero-budget failure, reopens the gate through the
controller, then repeats with the fast fallback. It checks method results and
scratch preservation. It allocates the entire selected high-memory arena, writes
a distinct U32 value at each 4 KiB interval and a marker at the last payload byte,
checks them, and releases the allocation. This is a range/aliasing check, not an
exhaustive DRAM test. Generated executable regions pass the 386 instruction audit.

`--memory` also covers extended reservations, the ceiling, scratch exclusion, and
conventional fallback. VGA's full pixel comparison and all native loader cases
exercise high-memory integration. The test harness uses QEMU's 486 model with
8 MiB RAM; physical 386SX/DX validation and timings remain outstanding.

The production boot path, PIC/PIT interrupts, input initialization, page/task heap
ownership, and full OS memory measurements remain pending. Conservative legacy
limits may be refined with additional verified machine-profile information; no
full-system 8 MiB or self-hosting 16 MiB claim follows from these unit runners.
